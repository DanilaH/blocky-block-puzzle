# Reference Teardown Protocol — видео/игра/GIF/скриншот как источник требований

**Scope:** любое поручение «сделай как на референсе», «в оригинале удобнее», «повтори feel», «сравни механику/анимацию/выдачу», а не только подбор арт-стиля. Дополняет [Visual Preproduction](https://github.com/DanilaH/mini-games-kit/blob/e2382670fbd5c2aa76462fea688c60de2b067392/docs/visual-preproduction/AGENT_PROTOCOL.md), [Store reference protocol](https://github.com/DanilaH/mini-games-kit/blob/e2382670fbd5c2aa76462fea688c60de2b067392/docs/store-presence/AGENT_PROTOCOL.md) и [Reverse Engineering research](https://github.com/DanilaH/mini-games-kit/blob/e2382670fbd5c2aa76462fea688c60de2b067392/docs/puzzle-design/research/puzzle-reverse-engineering-2026-11-11.md), не заменяет их.

> Увиденная сцена, предположение о невидимом алгоритме, рекламный ролик и настоящая игровая сессия — разные источники. Задача агента — **воспроизвести намеренно важное поведение**, а не сделать картинку в похожих цветах или угадать код конкурента. Не переносить защищённые ассеты, чужой код или узнаваемые фирменные элементы; адаптировать общие принципы взаимодействия с оригинальными материалами.

## A. Сначала доступ и provenance

Собрать минимальный source register:
- Exact URL или прикрепленный файл, вид контента (реальный gameplay, capture другого пользователя, промо, прототип, статичный скрин, рендер), имя игры, дата, известные версия и устройство/ориентация.
- **Что действительно просмотрено**: URL открыт / GIF декодирован / реальные видеофреймы воспроизведены / источник недоступен. Если нет доступа, честно записать NOT INSPECTED и не утверждать «в оригинале работает так».
- Имеется ли разрешение использовать материал как **референс**, а не встраивать чужие оригинальные изображения/музыку/текст в игру. Never download/copy proprietary assets into release.
- Если предоставлены несколько примеров, отделить эталон **поведения** от вдохновения **стилистикой** и от магазинной рекламной нарезки.

Сохранить source URL/file SHA/timecode, ссылку на текущую реализацию и конкретный build при сравнении. Отсутствие видео/audio не восполнять догадкой.

## B. Разобрать реальный UX в действие — не только в статику

Смотреть **короткие полные эпизоды** (если пользователь не указал другое):
1. Холодный старт → первое игровое действие.
2. Обычное действие: откуда палец/мышь берёт объект, где проходит pointer, как preview/drag/click соотносится с реальным hit area.
3. Как система реагирует при **промахе**, неразрешённом ходе, коротком тапе, отпущенном указателе, отмене и выходе с поля.
4. Текущая и предыдущая фигура/карта/содержимое; откуда появляется новый объект и куда реально движется старый.
5. Успешное действие → задержка до feedback → положение остальных элементов → next available action.
6. Более сильная награда, поражение, возрождение, undo/hint/restore (если применимо).
7. Узкий/широкий экран и жесты, особенно скролл/зум, баннер, клавиатура; если референс даёт только одну геометрию, другие UNKNOWN.
8. На длинных партиях: несколько соседних выдач/уровней, разнообразие/поток наград; **не выводить скрытую policy из пары примеров**.

**Минимум 3 подтверждённых эпизода на ключевой спорный жест**, если материал позволяет, плюс один неприятный/пограничный случай. Число — предпочтение QA, а не обязательный норматив и не повод требовать новые видео у владельца, когда достаточно одного воспроизводимого факта.

### Capture unit

| Source/frame/timecode | Ожидание пользователя | Наблюдаемое состояние до | Gesture/pointer/тайминг | Реальное состояние после | Evidence status |
| --- | --- | --- | --- | --- | --- |
| | | | | | OBSERVED / INFERRED / UNKNOWN |

На быстром drag/картном flip полезен sequence: **before → active gesture → accepted state → reward settled**. Один красивый кадр показывает только статическую композицию.

## C. Измерять как продукт, а не «похоже» по впечатлению

Отдельные оси:
- **Layout:** viewport, board occupancy, относительные размеры, распределение пустого пространства, safe areas, элементы сверху/снизу, реальная плотность кнопок/карт.
- **Input semantics:** tap vs hold vs drag vs tap-select-target; pointer capture, точка привязки, ghost/drop preview, движение за пределами исходного объекта, отмена.
- **State provenance:** фигура/карта появляется *из своей колоды или лотка*, действительно уменьшается стопка, виден хвост предыдущих, фокус/скролл сохраняется.
- **Motion grammar:** тайминг и порядок: начало → физическое движение → contact → settle → next action; easing, overlap/паузы/возможность пропуска. Не выдавать benchmark миллисекунд без измерения на сравнимом устройстве.
- **Feedback:** звук/вибрация/визуальное подтверждение, контраст между обычным и редким достижением, отсутствие дублирования и UI-скачков.
- **Game logic:** реальные ограничения, количество доступных решений, последствия ошибки, повторяемость и контроль рандома. **Не декомпилировать** чужое приложение и не выдавать свои гипотезы о скрытом директоре за факты.
- **Accessibility:** читаемость, цветовое кодирование, размер настоящей зоны, reduced motion, опция без сложного drag — только где оправдано.
- **Identity/production:** какие общие закономерности передать оригинальным текстом, визуалом и звуком, без копирования фирменной айдентики.

При необходимости описать разницу в пикселях/относительных долях, но только для **измеренных** кадров и сопоставимой геометрии. Реальные суммы очков, эффекты, уровни и UX опирать на настоящие записи.

## D. Reference gap: наблюдение → наш дефект → решение

Таблица, которой агент руководствуется перед кодом:

| Референс (свидетельство) | Наш build (свидетельство) | Gap | Требуемое поведение | Минимальная правка | Как проверить |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

**Статусы:** MATCH / GAP CONFIRMED / REFERENCE UNKNOWN / INTENTIONAL DIFFERENCE / REJECT COPY. Не приписывать референсу не наблюдавшуюся особенность ради оправдания своего решения.

Важная проверка: **не нужно ли изменить фундаментальный contract ввода/расположения, а не рисовать эффект поверх неправильной модели?** Пример: карта должна **переворачиваться из колоды**, а не прилетать «из пространства»; исправление одного easing не закрывает ошибку origin. Или drag следует за пальцем на всём допустимом экране, а не исчезает внутри чужого контейнера — нужен pointer/layout fix, не новый спрайт.

## E. Приоритеты и утверждение дизайна

- На воспроизводимый пользовательский дефект/явное требование владельца агент может сделать локальную правку с соответствующим regression test без отдельного художественного выбора.
- На **новый** сеттинг, маскота, крупную переработку графики или новую core policy — показать 2–3 продуманных варианта на тех же игровых состояниях, риск и цену; владельцу принадлежит окончательное арт/продуктовое утверждение.
- Если оригинал нельзя открыть, использовать только доступные доказательства и честную гипотезу/нейтральный прототип. Не фальсифицировать «покадрово проверено».
- Не пытаться оптимизировать несравнимые цели одновременно; лучше 1–3 главных confirmed gaps, чем сорок декораций.
- Не допускать copyright confusion: принципы/геометрия/feel можно изучать; чужие исходные изображения, музыка, метки/брендинг и код в production — нет.

## F. Проверка уже на нашем исполняемом проекте

После правки:
1. **Сравнимый state:** тот же режим, seed/раздача, размер/ориентация, последовательно реальные pointer/touch действия, а не нарисованная анимация.
2. **Side-by-side** исходный и новый before/action/after с точной provenance; 1–3 коротких видео/GIF/скриншота при необходимости. Если исходный доступен только в одном кадре, так и указать.
3. **Input regression:** short tap, drag outside, release, cancel, next action, fast repeat, resize/rotation, small portrait and landscape, persistence/Undo.
4. **Rules/economy/SDK regression:** no unrequested change in balances, ads, save structure, callback behavior, score.
5. **Feel:** независимый человек/владелец или реально recorded phone comparison для спорного «приятнее/как оригинал». Бот или browser picture не доказывает ощущение на телефоне.
6. **Owner-facing outcome:** что точно совпало, что сознательно осталось отличным и что проверить позже.

**Не читать весь этот протокол для bugfix без референса.** Он подключается автоматически именно когда задача содержит указанный образец/требование «как там». В результате должен появиться доказуемый выбор изменений, а не тысячи описательных строк.
