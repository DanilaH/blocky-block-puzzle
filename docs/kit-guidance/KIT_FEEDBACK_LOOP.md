# Kit Feedback Loop — заметить, доказать и сообщить о переиспользуемой доработке

**Задача:** потребитель mini-games-kit не должен молча оставлять улучшенные универсальные механизмы только внутри одной игры, но и не должен отправлять каждую локальную фичу в общий SDK. Этот протокол применяется в конце **существенного изменения кода** и при обнаружении копии уже существующего kit-примитива.

## 0. Четыре безопасных исхода и один реальный перенос

- **NONE:** чисто проектная механика/баланс/контент/визуал, kit не изменился и повторное использование маловероятно. В итоговом ответе достаточно «Kit impact: NONE».
- **REUSE:** агент обнаружил и использовал существующий компонент mini-games-kit, сохранив project policy в игре. Указать импорт, kit ref, решение, test.
- **IMPROVE:** найден баг или недостающая контрактная возможность уже существующего **общего** модуля. Есть воспроизведение из реального consumer, а не новая идея без кода. Создать короткий proposal и направить owner: что сломано в kit, как исправить, какие другие consumers заденет. Для **исправления подтверждённого бага** достаточно одного качественного независимого воспроизведения, не требовать второго сломанного продукта.
- **CANDIDATE:** создан локальный механизм, потенциально общий, но пока только в одной игре. **Не переносить автоматически**. Предложить повторное использование по второму независимому реальному случаю и отделить semantic invariant от правил конкретной игры.
- **EXTRACTED:** общий код действительно перенесён в kit, прошёл собственные tests/API docs, подключён к реальным consumers с закреплёнными версиями и миграцией; показать ссылку на конкретный PR/commit. Нельзя выдавать написанный proposal за extraction.

Статус **MISSING / UNKNOWN** допустим, когда кит недоступен/не прочитан: агент не должен врать «проверил весь kit».

## 1. Cheap discovery: проверить до нового компонента

При любом существенном инфраструктурном изменении:
1. Посмотреть [Public API](https://github.com/DanilaH/mini-games-kit/blob/e2382670fbd5c2aa76462fea688c60de2b067392/docs/API.md), доступные docs выбранных subpaths. Не делать три отдельных helper-а для уже имеющегося layout/snapshot/receipt/activity/feel.
2. Сравнить **действующий контракт** и **локальную задачу**, а не похожие названия функций.
3. Если kit уже имеет механизм, проверить pinned dependency/peer/version и реальную совместимость; consumer может использовать старый закреплённый commit — не переписывать dependency незаметно.
4. Если кит отсутствует offline, не писать «kit ничего такого не содержит». Пометить discovery UNKNOWN и указать, какой доступ нужен, либо работать с локальным уже закреплённым пакетом.

### Быстрые сигналы KIT IMPACT

- Local bugfix исправляет listener disposal, input/pointer capture, Android Back, ad resume, asset preload, save receipt, deterministic replay, responsive/safe-area behavior → **проверить** имеющийся примитив.
- Одна и та же utility вручную скопирована во второй проект и появилась проблема поддержки → **CANDIDATE** extraction.
- Исправлено поведение kit export, но код пока патчен локальным wrapper/fork → **IMPROVE** с планом upstream, даже если это одна игра.
- Изменены частные правила выдачи, умственная сложность контента, расстановка фигур, экономика/адвертайзинг, иллюстрации → обычно **NONE**, даже если работа оказалась удачной.
- Процесс помог дважды находить правильные исследования без кода → улучшить **методологию/роутер** в kit, **не создавать SDK**.

## 2. Порог переноса и границы владения

**Existing common primitive, regression fix:** 1 воспроизводимый consumer + независимый test + совместимый API либо объяснённый deliberate breaking change.

**New common primitive:** как правило ≥2 реальных независимых consumers с одинаковым **поведенческим** контрактом, доказанной экономией сопровождения, тестами и границами project policy. Исключение — явное архитектурное решение владельца с обоснованием, а не «LLM придумала универсальную абстракцию».

**Research documentation/protocol:** реальная повторяемая ошибка агента может оправдать изменение Task Router уже после одного случая — это не публичный runtime API.

В самом kit для нового экспорта обязательно: [Contributing checklist](https://github.com/DanilaH/mini-games-kit/blob/e2382670fbd5c2aa76462fea688c60de2b067392/CONTRIBUTING.md), [Public API](https://github.com/DanilaH/mini-games-kit/blob/e2382670fbd5c2aa76462fea688c60de2b067392/docs/API.md), focused docs в docs/, tests, provenance/source SHA, semantic differences, migration/compatibility. Стили, rewards, balance, content, host-specific SDK constraints принадлежат consumer, если нет общего доказанного механизма.

**Никаких побочных массовых изменений всех игр** при обновлении kit: в каждом consumer закреплён собственный SHA. Upgrade требует отдельного намеренного PR/проверки, иначе reproducibility нарушится.

## 3. Формат сообщения владельцу (5 строк, а не огромный отчёт)

**KIT IMPACT: IMPROVE** (пример)

- **Что заметили:** одинаковая ошибка pointercancel в локальной сцене и текущем kit interaction helper.
- **Kit current feature:** путь до существующего документа/функции; pinned revision consumer.
- **Доказательства:** exact source repo HEAD, воспроизведение и test, чем этот кейс общий.
- **Что предлагаю:** исправить минимальный общий контракт и локальную интеграцию, какие API/docs/tests проверить.
- **Статус:** CANDIDATE PROPOSAL (не внедрено) / PR создан / PR принят, номер и ссылка. **Нужна ли владелец-approval:** когда затрагивает другие игры/публичный API/публикацию — да.

Для **CANDIDATE** указать «второй consumer пока не найден» и *какой повтор подтверждал бы перенос*. Для **NONE** просто одна строка.

## 4. Куда писать и когда переносить

- **Consumer:** docs/PROJECT_DECISIONS.md фиксирует именно принятую локальную архитектуру. При повторяемом предложении можно создать небольшую запись docs/KIT_CANDIDATES.md с source commit, triggered behavior, proof, consumer count, estimated complexity, owner decision. **Не создавать этот файл пустым при каждой новой игре.**
- **Kit:** если владелец одобрил upstream change, отдельный PR с tests/docs/API и независимым replay существующих consumers. Если только гипотеза — issue/proposal вместо кода. Создание issue/PR требует реального проекта, соответствующих прав и не должно подменять предложение исполнением.
- **Final owner report:** всегда указать KIT IMPACT в конце существенной задачи, особенно когда обнаружена новая общая возможность или изменена существующая. Не скрывать из-за успешного browser теста.

## 5. Независимое опровержение перед extraction

- Совпадает ли **семантическая** задача или только имя (например, два разных Help UX)?
- Достаточна ли существующая [API](https://github.com/DanilaH/mini-games-kit/blob/e2382670fbd5c2aa76462fea688c60de2b067392/docs/API.md) уже сейчас и не стал ли новый wrapper бессмысленным?
- Добавит ли общая abstraction больше maintenance, чем две короткие локальные реализации?
- Можно ли импортировать без дополнительных framework/native dependencies и не подтягивает ли новый экспорт project policy?
- Есть ли независимый test повторяемости, очищения listeners, error/retry, save migration и performance при частом вызове?
- Зачем владельцу это нужно **в следующей игре**, а не просто для красивого пакета?
- Как показать, что новая универсальная фича уже есть в kit и consumer её действительно импортирует (не только Git commit)?

**Главный критерий:** меньше повторных ошибок и ручного труда, не максимальное число экспортов или PR. Хороший consumer агент обязан замечать upstream возможности, но не обязан создавать их без согласования.
