# Реальная трасса POCO0.52 — 08.11.2026

## Полученный результат

Короткая проверка завершилась на физическом POCO M6 Pro: package0.52, Android15/WebView156, Mali-G57 MC2, canvas896². ZIP успешно содержит отчёт и JSON-трассу29145360байт/170126events. Native status ready=true/error пустая; parser/loss counters и перезаписи обоих буферов нулевые. USB больше не нужен для этого сбора данных. Проблема воспроизведена, исправления пока не выпускались.

## Что видно в физической трассе

Логика хода быстрая: в untraced расчёт1.1мс, атомарное сохранение11.6мс (wall, асинхронное), первый placementRender3.1мс; boardDraw max1.2мс. LongTask entries нет, однако это не означает отсутствия нагрузки на renderer main.

В окне650–1400мс после контрольной метки возвращения commit:119 событий `Blink.ForcedStyleAndLayout.UpdateTime`, суммарно206.331мс wall/190.376мс thread CPU, максимум13.28мс. Они идут внутри rAF/`v8.callFunction`, а не только после JS в обычном lifecycle. Самый большой `ProxyMain::BeginMainFrame` здесь29.861мс. Это существенная работа, которой счётчик `boardDraw` не покрывает.

Одновременно Android draw path ждёт зависимости: `DrawFn_DrawGL` достигает53.071мс, `ScheduleOnVizAndBlock` в полном захвате50.120мс; `WaitSyncToken` —33.893мс с очень малым thread CPU. Это наблюдение о синхронизации/передаче графических работ. **Оно не измеряет GPU execution time и не доказывает конкретную перегруженную текстуру или GPU shader.**

Длинный351мс `v8.callFunction` в начале settle относится к worker thread, не к CrRendererMain; нельзя выдавать его за351мс блокировки игрового JS. В основной трассе есть GPU/raster/compositor events, но нет полного системного sched/GPU counters для однозначного разделения CPU scheduling и GPU execution.

Trace export удалил пользовательские имена: наши три записи видны как `performance.mark`, с интервалами18.999мс и2401.107мс. Последовательность соответствует start/committed/end из контролируемого теста. Окна трассы отсчитаны от второй метки; **точного общего смещения с rAF timestamps из report нет**, поэтому совпадения отдельных кадров с конкретными native slices не объявляем. Вложенные spans и времена разных потоков не складываем в независимую стоимость.

## Проверенный кандидат: чтения viewport внутри эффектов

`Atmosphere.draw` читает `innerWidth/innerHeight` на каждом тике, `Festival.draw` делает то же для очистки canvas. Смена темы параллельно анимирует стили DOM. В мобильном пути Blink чтение viewport может вызывать `UpdateStyleAndLayout`: [Chromium LocalDOMWindow/GetViewportSize](https://chromium.googlesource.com/chromium/src.git/+/176210e8ce99f1165437676c5623a03cadd8d574/third_party/blink/renderer/core/frame/local_dom_window.cc). Это объясняет, почему прежний desktop viewport недостаточно отражал mobile path; размер окна сам по себе не включает `isMobile`/mobile viewport behaviour.

Выполнен изолированный диагностический прогон: Linux Chromium,392×872/DPR2.75, **isMobile=true**, та же игра/позиция, порядок baseline/cache/cache/baseline. Только в browser init script заменены глобальные viewport getters на кеш, обновляемый при resize/DOMContentLoaded; код приложения не менялся. [Скрипт](../../scripts/probe-viewport-052.mjs), [результаты](phone-trace-052/viewport-getter-probe.json).

Это подтверждает источник лишней layout/style-работы в данном пути. Глобальное переопределение getters — **диагностический инструмент**, не финальная реализация. Все12 ходов сохранили1574/тему5. Количество длинных интервалов software graphics меняется мало и не даёт основания объявить устранение лага или выигрыш на Mali.

## Следующая правка

1. Вынести viewport dimensions из покадровых функций Atmosphere/Festival в локальный кеш, обновляемый по resize/возврату/запуску эффекта; не переопределять глобальные browser APIs в приложении.
2. Проверить возврат из фона, поворот и размер canvas/поле; сохранить внешний вид эффектов и их разрешение.
3. Повторить тот же короткий тест на POCO. Сравнить forced style/layout и untraced интервалы; отдельно проверить, остались ли native waits.

Графический тракт пока не локализован до одного эффекта. Если forced layouts уйдут, а длинные ожидания останутся, следующий эксперимент должен адресовать конкретные canvas/compositor зависимости из новой трассы, а не возвращаться к уже отклонённым подготовленным кадрам.
