# Диагностика просадки полной очистки в preview 0.47

Дата: 07.11.2026. Исходники приложения совпадают с APK-коммитом `561e8c7`. Продолжение [исследования источников](PERFORMANCE_RESEARCH_2026-11-07.md). Игровой код, ассеты, разрешение, flow-v4 и выданный APK не изменены.

## Результат

Просадка воспроизводится без следующего drag, без смены темы и после первого показа. В данном облачном окружении основной подтверждённый участок ожидания — графический командный буфер Chromium во время рендеринга содержимого Phaser. Новая трасса раскрывает старый долгий `Commit`: внутри него есть `ImplementationBase::WaitForCmd` и `CommandBufferProxyImpl::WaitForGetOffset`.

Самый полезный следующий объект оптимизации — совместная стоимость текстурных VFX и световых примитивов внутри WebGL-поля. Удаление любого из этих слоёв в диагностике существенно облегчает эпизод. Отключения не являются допустимым готовым исправлением: они убирают часть изображения. Ни одна оптимизация для пользовательской сборки этим проходом не принята.

## Стенд и границы доказательства

- Chromium 141.0.7390.37, Linux, SwiftShader через ANGLE/Vulkan; viewport 390×844, DPR 2, фактический WebGL canvas 768×768.
- Phaser 4.2.1, `fps.limit=60`, MSAA выключен; параметры GL сохранены в данных. GPU timer query недоступен.
- Звук и haptics выключены одинаково во всех условиях. Это исследование графики, не полный телефонный плейтест.
- Постановочная сцена: O3 замыкает три строки и три столбца, одновременно очищаются 39 клеток. В варианте без полного обнуления остаётся ещё одна клетка. Полная очистка переключает оформление 0→5; вариант общего праздника — 2. Другие исходные оформления и варианты праздника этим набором не покрыты.
- Выполняется настоящий `commit` приложения и настоящая атомарная запись IndexedDB. Следующий ввод по умолчанию отсутствует. Подсказки/реклама не вызываются.
- Для повторного показа профиль восстанавливается через `ProfileStore.update`, эффекты завершаются, затем выдерживается 2100 мс. Страница, Phaser и WebGL-контекст сохраняются. Первый показ означает первый в данном контексте; глобальные кеши браузера/ОС не очищались.
- Каждый основной фактор проверен в трёх контекстах, по два показа: первый и повторный. Порядок условий во втором круге развёрнут. Внутри контекста первый всегда предшествует повторному, поэтому один этот фактор не отделён от общего времени жизни контекста.
- Диагностика внедряется Vite-плагином в памяти, без правок `src`. Production-проверка использует отдельный инструментированный minified build в `/tmp`, а не побайтово исходный APK bundle. Внешние хуки способны влиять на время; в пределах сравнения они одинаковы. Трассы сняты отдельно от сравнений без tracing.
- Косметический `Math.random` не фиксировался; выборка мала. Приведённые диапазоны — наблюдения отдельных запусков, не доверительные интервалы и не гарантия Android FPS.

Основная серия — **132 эпизода**: 126 без tracing и 6 с tracing. Ошибок страницы — 0. Для всех all-clear условий, включая диагностические отключения, получен один и тот же хеш сохранённого игрового состояния после исключения `gameId`. Замораживание темы меняет только представление: результат хода и выбранное оформление в сохранении остаются теми же.

## 1. Смена темы — не обязательное условие просадки

Ниже повторные показы, три контекста, окно 2200 мс. «Длинные интервалы» — rAF >25 мс на этом 60-Гц стенде. Это рабочий порог сравнения, не универсальная метрика для телефона. Сэмплы представлены временным рядом; p95 не приравнивается к постоянным 30 FPS.

| Условие, dev | p95 rAF, мс | Число интервалов >25 мс |
|---|---:|---|
| Полная очистка + тема | 33,4 во всех | 23 / 19 / 18 |
| Та же очистка, тема визуально зафиксирована | 33,4 во всех | 20 / 18 / 20 |
| Шесть линий, одна клетка остаётся | 16,8 во всех | 5 / 3 / 5 |
| Только смена темы на пустом поле | 16,7–16,8 | 0 / 0 / 0 |
| Обычная постановка | 16,7–16,8 | 0 / 0 / 0 |
| Бездействие | 16,7–16,8 | 0 / 0 / 0 |

Таким образом, сочетание полной очистки и перехода темы было слишком широким названием симптома. В этом сценарии достаточно самой постановки полной очистки; переключение темы отдельно на пустом поле дешёвое. Это не проверка стоимости перехода темы на произвольно заполненном поле.

## 2. Прогрев реален, но не устраняет полную очистку

При первом полном эффекте обычно регистрируются 10 `compileShader` и 5 `linkProgram`; при первом многолинейном — 8 и 4. В повторных показах первой серии эти вызовы отсутствуют. В последующих сериях отдельные повторные показы всё же создавали дополнительные варианты; назвать второй показ гарантированно полностью прогретым нельзя.

Многолинейный эпизод после повторения заметно облегчается. У полной очистки и при отсутствии новой компиляции p95 остаётся около 33,4 мс. Добавлять скрытый прогрев как «решение всей просадки» оснований нет.

## 3. Desktop/mobile texture units различаются, но переключатель проблему не решил

Стандартный desktop действительно использует 16 параллельных текстур. Android UA переключает определение устройства в `desktop=false/android=true` и штатный лимит становится равным 1. Физический GPU остаётся тем же SwiftShader: это проверка программной ветки, не Android-устройство.

Повторные all-clear показы:

| Настройка | Максимум draw calls в одном render | p95, мс | Интервалы >25 мс |
|---|---|---|---|
| Штатный desktop, 16 | 2 / 2 / 2 | 33,4 / 33,4 / 33,3 | 20 / 17 / 17 |
| Принудительно 1 | 87 / 90 / 85 | 33,4 / 33,4 / 50,1 | 23 / 20 / 24 |
| Принудительно 2 | 18 / 18 / 18 | 33,4 во всех | 20 / 20 / 22 |
| Принудительно 4 | 7 / 7 / 7 | 33,4 / 33,3 / 33,4 | 20 / 20 / 22 |
| Android UA, штатно 1 | 84 / 80 / 76 | 33,5 / 33,4 / 33,4 | 19 / 18 / 24 |

Простое изменение лимита не прошло даже скрининг. Низкое число draw calls на desktop не доказывает низкую стоимость пикселей или исполнения команд. Текстурный атлас мог бы уменьшить число переключений в мобильной ветке, но его реальный выигрыш и отсутствие ухудшения на телефоне ещё не измерены. Перепаковывать все ассеты по этим данным преждевременно.

## 4. Уточнена часть сцены, которая создаёт нагрузку

Все отключения ниже исключительно диагностические. `noRender` пропускает отрисовку содержимого SceneManager, сохраняя update, подготовку представления, сохранение, DOM, внешние canvas, pre/post-render и жизненный цикл менеджера. `noVfx` и `noInk` прячут соответствующие изображения после обновления их параметров: JS-подготовка слоя продолжает выполняться.

| Условие, dev | Повторный p95, мс | Интервалы >25 мс |
|---|---|---|
| Полная сцена | 33,4 во всех | 21 / 23 / 21 |
| Без отрисовки содержимого WebGL-сцены | 16,7–16,8 | 0 / 0 / 0 |
| Без внешнего Festival burst | 33,3–33,4 | 17 / 20 / 19 |
| Без ambient-рисунка | 33,4 во всех | 18 / 20 / 22 |
| Без текстурных VFX внутри поля | 16,8 во всех | 5 / 3 / 6 |
| Без слоя световых примитивов SpriteInk | 16,7–16,8 | 4 / 3 / 1 |

Полная сцена имеет максимум два draw calls за render. Отключение SpriteInk оставляет этот максимум равным двум, но облегчает кадры. Это сильный довод против объяснения всего симптома одним количеством draw calls. Снижение стоимости исполнения/площади и наложения прозрачных элементов — рабочая гипотеза, а не измеренная GPU fill-rate.

### Проверка production

| Условие | Повторный p95, мс | Интервалы >25 мс |
|---|---|---|
| Полная очистка | 33,4 / 33,4 / 33,4 | 20 / 21 / 20 |
| Многолинейная без полного обнуления | 33,3 / 16,8 / 16,8 | 7 / 5 / 4 |
| Без текстурных VFX | 16,8 / 33,3 / 16,8 | 5 / 8 / 3 |
| Без SpriteInk | 16,8 / 16,8 / 16,8 | 2 / 2 / 3 |

Направление воспроизвелось и в production build, однако удаление VFX не гарантирует p95 16,8. По этой причине главный вывод опирается также на число длинных интервалов и сохранённые временные ряды, а не на один процентиль.

## 5. Трасса раскрыла ожидания внутри Commit

Отдельные повторы с tracing, окно 3500 мс. Ниже один повторный эпизод каждого условия. Все числа — длительности span браузерной трассы, не чистое время шейдера. Вложенные длительности **нельзя складывать**.

| Span на CrRendererMain | Полная очистка | Контроль без WebGL-содержимого |
|---|---:|---:|
| Commit: сумма / максимум, мс | 2072,7 / 30,0 | 743,1 / 8,0 |
| WaitForGetOffset: сумма / максимум, мс | 1627,5 / 28,0 | 210,0 / 3,7 |

В `CrGpuMain` у полной очистки задачи также существенно длиннее. На этом стенде графический API исполняется программно на CPU. Вывод: наблюдаемое торможение включает ожидание графического командного конвейера, а не только выполнение функций игрового JS.

У многолинейного контрольного эпизода сумма ожиданий за всё окно тоже велика, несмотря на меньшее число пропущенных дедлайнов. Следовательно, одна сумма `Commit`/wait не является достаточной метрикой плавности: важны распределение и пики. Подробная разбивка — `performance-probe-047/trace-summary.json`.

Таймер GPU недоступен, поэтому пока не отделены точная стоимость fragment shader, программной растеризации, передачи ресурсов и синхронизации представления. Нет основания объявлять найденным дефект физического Android GPU или баг Phaser.

## 6. Следующий узкий кандидат

Имеет смысл исследовать **площадь прозрачной отрисовки и наложение больших подсветок внутри поля**, сохраняя изображение, ритм и разрешение. В `BoardScene` полная очистка накладывает общий свет, большое кольцо/вспышку и клеточные световые хвосты; эти группы одновременно используют VFX и SpriteInk. Сначала измерять/сравнивать отдельные группы, затем проверять вариант с меньшим лишним покрытием прозрачных областей. Низкий draw-call count не отменяет этой гипотезы.

Условия дальнейшего принятия: тот же результат игрового хода; визуальное сравнение на одинаковых временах; отсутствие потери слоёв/частиц и ухудшения чёткости; парное сравнение на новых повторах. Сокращение картинки, снижение DPR или отключение слоя не засчитываются как исправление. Выигрыш на SwiftShader не доказывает выигрыш телефона. Масштабную перепись движка/эффектов до одного аппаратного замера не рекомендую.

## Данные, воспроизведение и завершение этапа

- `scripts/audit-performance-probe.mjs` — изолированный запуск dev/production и условия экспериментов.
- `scripts/performance-probe/browser.mjs` — диагностические хуки, маркеры и измерения.
- `scripts/performance-probe/summarize.mjs` — упаковка результатов с сохранением rAF-временного ряда.
- `performance-probe-047/measurements.json` — все 132 эпизода: настройки, серии rAF, статистики, GL-счётчики, маркеры, результаты хода и хеши состояний.
- `performance-probe-047/trace-summary.json` — отобранные span расширенных трасс.
- `performance-probe-047/README.md` — точные команды и ограничения протокола.

Большие промежуточные raw JSON и gzip-трассы не входят в удалённый пакет; опубликованы данные измерений и компактные выдержки. Их можно переснять приведёнными командами. Исходный APK 0.47 остаётся рабочей выдачей. Новых исследований директора и новых политик выдачи нет.
