# POCO 0.57 — отдельного виновника среди четырёх деталей нет

## Результат

Все 18 эпизодов валидны. Ни отключение вспышек счёта, ни подписи, ни CSS world-палитры, ни плашки новой темы не достигло заранее установленного порога в обоих порядках. Крупные no-reward-dom и no-theme снова помогают. Это исключает принятие одной из четырёх простых правок как готового исправления; не доказывает, что их вклад равен нулю.

Причина взаимодействия ещё не установлена. Не проверены отдельно перелёт очков и импульс новой темы; no-theme также замораживает оформление поля/материалов/фоновых слоёв, которых no-dom-palette не касается. Возможен суммарный выход нескольких одновременно работающих частей за кадровый бюджет. Ни этот вариант, ни «конфликт WebView с Phaser» не объявляются доказанным диагнозом.

## Сравнение на телефоне

Число RAF-интервалов **дольше 33.4 мс** в 2.4 сек после хода; включение по пересечению интервала с окном. Это не прямой замер физического показа кадра или времени исполнения GPU.

| Условие | Первый проход | Обратный проход |
|---|---:|---:|
| Все эффекты, контроль до / после | 6 / 6 | 6 / 7 |
| Без вспышек счёта | 1 | 6 |
| Без подписи награды | 5 | 5 |
| Без смены CSS world-цветов | 8 | 5 |
| Без плашки темы, с прежним импульсом | 7 | 7 |
| Без всего блока наград и связанных вспышек | **1** | **1** |
| Без смены всего видимого оформления | **1** | **2** |

Вспышки проходят цель только в первом порядке; менять основной критерий после получения результата нельзя. No-reward-dom уменьшает число длинных интервалов относительно среднего своих контролей на 83.3% / 84.6%, no-theme — на 83.3% / 69.2%; максимум также укладывается в исходное правило. Остальные варианты порог не проходят. P95: no-reward-dom 16.9 / 16.9 мс, no-theme 16.8 / 16.8 мс; обычные контролы около 25.2–25.3 мс.

В no-reward-dom остаётся по одному интервалу 33.6 / 42.0 мс. В первом no-theme есть 50.4 мс. Полного отсутствия рывков нет даже в полезных больших отключениях. Стабильность по числу >33.4 мс также не означает отсутствия прочего drift: количество RAF-интервалов у контролей 218→174 и 162→165; температуры/частоты/фоновой нагрузки в отчёте нет.

Из 25 длинных интервалов четырёх обычных контролей 22 заканчиваются между 320 и 1400 мс. Это совпадает с областью перекрытия праздника и перехода темы, но само совпадение не устанавливает причину. По дискретным интервалам около 33.6 мс нельзя объявлять устранение проблемы по небольшому изменению одного счётчика.

Направление больших отключений повторилось в трёх отдельных сессиях 0.55–0.57. Числа между версиями не являются контролируемым A/B: renderer/переходы и состояние телефона различались. Они не объединяются в общий процент ускорения.

Native записан только для полного финального baseline, поэтому здесь нет причинного сравнения native работы с каждым отключением и нет атрибуции к одному DOM-элементу.

## Дополнительная локальная проверка заливки поля

В `BoardScene.setTheme` у родителя WebGL canvas остаётся самостоятельный inline `background-color` transition. Заморозка только CSS world-bg/ink/accent его не отключает. Этот путь проверен отдельной исследовательской Vite-подменой: новая конечная заливка сохраняется, а её fade выключен. **Это меняет промежуточную картинку и не является готовой реализацией.**

[Probe](../../scripts/probe-board-fill-057.mjs), [данные](rewards-057/board-fill-ablation.json): четыре независимые страницы A-B-B-A, по три настоящих clear; первый эпизод каждой страницы исключён. Восемь измеренных эпизодов, все 12 логических/renderer proof валидны, ошибок pageerror нет. Linux Chromium/SwiftShader, только это исследование, без параллельного browser/build запуска. Маленькая выборка не устанавливает производительность Mali.

| Вариант | Style, мс | Paint, мс | rAF, мс | CPU всего эпизода, мс |
|---|---:|---:|---:|---:|
| Прежняя заливка | 39.48 | 22.21 | 54.23 | 749.19 |
| Конечная заливка без fade | 39.28 | 19.47 | 61.22 | 763.76 |

Style/paint/rAF — прежнее окно 320–1400 мс, CPU — thread duration внешних renderer tasks полного эпизода, включая подготовку. Меньший Paint не дал общего стендового ускорения. Данных для выпуска этой правки как оптимизации нет; новая APK по этому результату не собиралась.

## Следующий ограниченный шаг

Рабочая гипотеза для следующего прототипа — **развести праздник очистки и смену оформления во времени**, сохранив оба набора эффектов. Логический ход, сохранение wardrobe и моменты поступления очков не задерживать; следующий ход не должен ждать декорацию. После завершения надписи/перелётов показать новую тему и её плашку. При новом all-clear/новой игре/паузе/фоне отменять устаревший визуальный запрос либо применять актуальное состояние, сохраняя существующие gameId/generation guards.

Это меняет ритм подачи и требует просмотра полного цикла, а не только финального скриншота. Сравнение старой и двухфазной постановки должно измерять **не менее 6 секунд**, чтобы включить отложенный переход и не спрятать рывок за прежним концом окна 2.4 сек. До измерения полного цикла и визуальной проверки прототип не принимается и не становится default. Это план прототипа, не реализованное исправление.

Отдельные перелёт и theme impulse остаются альтернативными непроверенными факторами. Если двухфазная постановка не даст выигрыша, их следует изолировать до большого переноса renderer. Переписывание Phaser или выпуск ещё одного кеша текста этим разбором не обоснованы.
