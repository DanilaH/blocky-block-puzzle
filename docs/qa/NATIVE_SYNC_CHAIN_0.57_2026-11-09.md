# POCO 0.57: цепочки ожиданий трёх долгих отрисовок

## Вывод

Из существующей записи установлена конкретная цепочка задержки: native-отрисовка WebView ждёт sync token, который освобождается в обработке растровых команд браузера. В двух из трёх выбранных отрисовок ожидаемая команда сама становится готовой к выполнению после сигнала из задачи создания shared image. Это прямые связи по flow ID, а не только совпадение времени.

**Конкретный игровой эффект по этому экспорту установить нельзя.** В нём нет идентификаторов DOM-узлов, слоёв, tile/resource/command-buffer и событий `Paint`. Кандидаты «перелёт», «подпись», «переход материалов», «внешний Canvas» не получили индивидуального причинного доказательства. Исправление производительности не заявляется; новый APK не выпускался.

## Исходные данные и отбор

Использован уже присланный native trace из результата 0.57; новых действий телефона не было. SHA-256 `f4659252d06609b90ba40aba0f4a265e5e77c745582343850b7bafcce71490d0`, 30 178 272 байта, 173 268 событий. Исходный source APK — `585c4225f8e4355db2b7abb2950da64f6a84dcb4`; это связь по прежней проверке APK, не встроенный commit отчёта.

Три generic `performance.mark` дают интервалы 24.106 и 2402.960 мс. Как и в прежнем разборе, их роль start/committed/end выведена из порядка и длительностей. Выбраны три самых длинных `DrawFn_DrawGL`, **начинающихся внутри committed–end**. Предшествующие 1.85 сек capture и экспорт результата исключены. Отдельный callback 44.092 мс до committed не подмешивается в список. Это callback-отрисовки, не измеренные физические показы кадров.

Все 9727 сохранённых flow-пар имеют ровно один start и finish; 49 проверенных parser/loss/buffer counters нулевые. Для каждого рассматриваемого ожидания проверены регистрация `SyncToken::Wait`, соответствующий finish, настоящий `SyncToken::Release`, содержащий producer flush и точный flow отправки `GpuChannel::Flush`. Отбор по времени сам по себе не создаёт причинную связь.

## Три отрисовки

Время относительно inferred committed, миллисекунды. «Всего ожиданий» — сумма непересекающихся дочерних `WaitSyncToken` внутри callback, не сумма всех вложенных renderer spans.

| Начало callback | Длительность callback | Всего sync-ожиданий | Самое долгое ожидание | Flow ID главного ожидания |
| --- | ---: | ---: | ---: | ---: |
| 747.895 | 47.719 | 39.048 | 31.253 | 5249 |
| 695.205 | 38.324 | 22.568 | 22.568 | 5064 |
| 853.668 | 36.290 | 20.739 | 15.791 | 5527 |

Разложение **самого долгого** ожидания каждого callback:

| Callback | До начала нужного producer | Работа producer до сигнала | Сигнал → возврат из wait |
| --- | ---: | ---: | ---: |
| 47.719 | 25.869 | 5.225 | 0.159 |
| 38.324 | 3.751 | 18.761 | 0.056 |
| 36.290 | 13.527 | 2.207 | 0.057 |

Части каждой строки складываются в длительность соответствующего главного ожидания. Полный `CommandBuffer::Flush` может продолжаться после нужного сигнала: например, во втором callback он занимает 21.857 мс, но до рассматриваемого release от его начала проходит 18.761 мс. Приписывать ожиданию весь flush было бы неверно.

Все три главных release находятся в flush с `RasterDecoderImpl::DoRasterCHROMIUM`. До relevant release в этих producer видны соответственно 5, 19 и 2 растровых вызова. Это **не** число DOM-элементов или слоёв: их идентичность отсутствует.

## Откуда берётся очередь

В callback 47.719 мс исходная отправка flush отмечена flow 5247 на renderer compositor внутри `MainFrame.Draw`, в 742.524 мс. Обработка нужного flush начинается только в 776.114 мс. Наличие отправки из compositor не устанавливает источник всех накопленных в ней команд.

Flow 5246 связывает `Scheduler::SequenceUnblocked` в 776.052 мс со стартом нужной scheduler-задачи в 776.092 мс. Само разблокирование выполняется под `SyncToken::Release` в предыдущей задаче, содержащей `SharedImageStub::OnCreateSharedImage`. Это подтверждает ресурсную зависимость. Аналогичная связь в третьем callback: flow 5524, release в задаче создания shared image, готовность 875.388 мс → запуск 875.419 мс.

За 25.869 мс перед запуском producer первого главного ожидания на его сервисном потоке наблюдаются:

- 7 задач с растровыми командами, 13.845 мс пересечения с этим окном;
- 7 задач создания shared image, 11.895 мс пересечения;
- 0.129 мс вне этих внешних задач.

Это непересекающийся **wall-time** задач одного потока, обрезанный границами окна. Он не является временем работы аппаратного GPU или CPU-utilization. Не каждая предшествующая задача автоматически является отдельным prerequisite именно этого token. В причинную цепочку включены только явно связанные события.

Chromium описывает sync token как порядок выполнения command buffers на CPU-стороне: декодирование, проверка и выдача команд драйверу. Освобождение token не равно завершению аппаратного GPU. Проверены [документация sync token](https://chromium.googlesource.com/chromium/src.git/+/refs/heads/main/docs/gpu/sync_token_internals.md) и [реализация Wait/Release](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/gpu/command_buffer/service/sync_point_manager.cc). Отсюда нельзя сделать вывод «Mali выполняет один шейдер 31 мс», обвинить Phaser или посчитать сумму вложенных категорий стоимостью кадра.

## Почему название эффекта потеряно

Проверено рекурсивно по всем event args:

| Данные | Что есть в записи |
| --- | --- |
| `layer_id` / `layerId` | 0 |
| `backendNodeId` / `nodeId` | 0 |
| `tile_id` / `resource_id` / `command_buffer_id` | 0 |
| `Paint` | 0 событий |
| `RasterTask` | 428 событий, у всех пустые args |
| `RasterDecoderImpl::DoRasterCHROMIUM` | 694 события, у всех пустые args |
| `SharedImageStub::OnCreateSharedImage` | 86 событий, у всех пустые args |
| `CanvasRenderingContext2D::FinalizeFrame` | 265 событий, у всех пустые args |

В записи также 717 событий с именем `FILTERED`. Проблема не решается другим парсером: нужных полей в файле нет. Увеличение лимита файла не вернёт уже отсутствующие данные.

У используемого Android WebView TracingController в [исходнике Chromium](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/android_webview/browser/tracing/aw_tracing_controller.cc) запуск явно передаёт `privacy_filtering_enabled=true`. У игрового Java-плагина выбираются категории и режим; отдельного переключателя этой фильтрации в нём нет. В текущем capture также отсутствует инструментированный Paint-путь. Добавление категорий не отключит встроенную фильтрацию. Проверен опубликованный исходник Chromium, не символизированная сборка конкретного WebView 156.

Второе ограничение: у 175 X-событий reported `tdur` превышает wall `dur` более чем на 50 мкс. Поэтому анализ сохраняет reported CPU как исходное поле, но не делит его пропорционально пересечению окна и не строит проценты загрузки. Главный вывод основан на flow и wall-интервалах, а не на этих CPU clock values.

## Что это меняет

Теперь известен механизм существенной части задержки выбранных callbacks: готовность графических ресурсов и обработка растровых команд в браузерном pipeline. Это более узкий результат, чем прежний общий `ScheduleOnVizAndBlock`, но **не индивидуальный виновник среди игровых эффектов**.

Общая трасса записана только для финального baseline. По ней нельзя причинно сравнить этот путь с успешными no-reward-dom/no-theme. Предыдущие контрольные отключения остаются полезным независимым фактом; они не превращаются в доказательство конкретного текста, перелёта или материала.

Следующая недостающая информация строго определена: запись на самом телефоне через DevTools/CDP с `gpu/cc`, инструментированными `Paint`/LayerTree и привязкой к DOM/Canvas. По слоям нужно видеть геометрию, источники invalidation/raster и compositing reasons, а вместе с ними — ту же sync-цепочку. Захват используется для атрибуции, его инструментирование не считается FPS-сравнением.

Для этого не требуется менять уже установленную 0.57: native-status подтвердил supported=true, а соответствующий исходник требует debuggable; используемый Capacitor включает WebView debugging для debug build, если не задан override. Проверенный путь доступа — [Chrome DevTools к WebView](https://developer.chrome.com/docs/devtools/remote-debugging/webviews) через USB и `chrome://inspect/#devices`. Реальная доступность USB/DevTools-сессии здесь не проверена: к пользовательскому телефону подключения нет. Не утверждается, что ещё один capture гарантированно локализует каждый эффект.

Новых APK, отключений эффектов и изменений приложения эта работа не вносит. Переписывать renderer только по полученному механизму не обосновано.
