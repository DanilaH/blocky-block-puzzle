Шесть пар A/B, порядок AB,BA,BA,AB,AB,BA. A — прежний scheduler180мс и
budget350мс/3млн; B — только автоматический ranking запрещён test-only
маршрутом source response. До эпизода praise запрещён в обоих вариантах,
одинаковые1200мс settle; затем A разрешён на новой revision, B запрещён.
Это контролирует стартовую нагрузку; не точная копия холодного запуска.
В production нет нового off/default/сдвига таймера. Длительность2000мс,
одна постановка, без следующего хода: результат фонового ranking не меняет
видимую похвалу текущего хода. Обе ветки уже содержат floating cleanup.

Отдельно2 trace-запуска A/B после untraced12; не смешивать их frame samples.
Сравнить exact authoritative after hash, score/streak/RNG, число lines,
worker start/result/cancel и per-phase wall times. Recorder RAF — cadence,
не фактический present/FPS WebView. Worker lifetime включает загрузку,
планирование/переписку, не CPU. Trace task durations тоже не выдаются за
thread CPU без соответствующих timestamp/counters. Одного меньшего числа
анимаций недостаточно для заявления ускорения.

Отчёт: все пары, направление p95/over33/over50, worker overlap; при смешанном
результате или отсутствии выигрыша оставить scheduler прежним, не подбирать
ещё несколько задержек/бюджетов. Подтверждение телефона остаётся открытым.
Проводить измерение последовательно, без параллельных builds/browser suites.

Уточнение границ фактического harness после выполнения:2000мс — ожидание
после durable commit; capture начинается перед вводом и включает также UI/
save wall time. Общие окна не строго одинаковы. Числа>33/>50 публикуются как
raw counts вместе с количеством RAF-интервалов, не как rate за ровно2сек.
Это не новая ветка/настройка алгоритма и не повторная выборка. Служебный
cancel probe после основной выборки не входит в статистику шести пар.
