# 0.58: один полный диагностический запуск

Это диагностическая итерация после неудачного двухфазного прототипа. Исправление лага не заявляется. Основа — обычная 0.57; отклонённые растровые буквы и двухфазная подача не возвращаются. Новая версия нужна для двух отсутствовавших переключателей и встроенного CDP-сборщика, чтобы не требовать от владельца USB/компьютер.

## Действия владельца

Обновить приложение, открыть **Пауза → Диагностика → Полная диагностика очистки**, нажать **Начать полную проверку**. Оставить экран открытым в текущей ориентации примерно на десять минут. После завершения нажать **Отправить результат** и прислать один `blocky-full-diagnostic.zip`. В течение проверки ничего выбирать и переставлять не нужно.

Если проверка полноты записи не пройдёт, сравнения не начнутся. Кнопка отправки сохранит конкретную ошибку; повторять запуск вслепую не требуется. Это первая проверка транспорта/метаданных, а не просьба вручную искать недостающие события.

## Матрица

Каждый эпизод использует одну известную реальную позицию POCO, два столбца, score 121→1574, wardrobe 1→5, вариант праздника 2. На каждый ход выполняются обычные расчёт/атомарная запись/render/reward пути в отдельной `blocky-clear-trace` базе. Обычная партия и backup не изменяются. Звук, вибрация, реклама и продуктовая аналитика в этом режиме отключены.

| Условие | Меняется только |
| --- | --- |
| baseline | Ничего |
| no-hud-flashes | Вспышка/масштаб счёта при поступлении очков |
| no-reward-decoration | Подпись, её движение и скрытая Classic эмблема; сумма и перелёт остаются |
| no-dom-palette | DOM world-палитра; поле, материалы, частицы, фон и плашка получают новую тему |
| no-theme-notice | Плашка темы; её импульс остаётся |
| no-point-flights | Перелёты сумм; появление суммы, подпись, моменты поступления и HUD сохраняются |
| no-theme-impulse | Добавочный импульс темы; плашка и смена оформления сохраняются |
| no-flight-or-theme-impulse | Эти два фактора вместе |
| no-reward-dom | Весь блок DOM-наград; поступление очков и добор числа сохраняются |
| no-theme | Всё оформление удерживается на теме 1; логическое wardrobe сохраняется как 5 |
| no-reward-or-theme | Оба больших блока вместе |
| no-ink | Декор поля |
| no-board-vfx | Частицы поля |
| no-festival | Внешний праздник |
| no-atmosphere | Фоновая анимация |

Получаются два запланированных 2×2: перелёт × импульс и весь reward DOM × вся тема. Дополнительно включены четыре прежние узкие reward/palette проверки и четыре renderer-слоя. Это конечная матрица по известному проблемному сценарию, а не обещание проверить все сочетания CSS-свойств, все варианты праздника, темы и реальные повороты устройства.

## Порядок и метрики

1. CDP-preflight с известным тестовым элементом: настоящий Paint должен связаться с его backend node и painted layer, native Draw и GPU flow должны присутствовать. Соединение после проверки закрывается.
2. Два прогревочных полноценных clear без трассировки.
3. Два противоположных порядка всех 14 условий **без CDP-трассы**. Контроль baseline перед первым и после каждых трёх кандидатов. Всего 40 сравнительных эпизодов.
4. По одному отдельному CDP-capture каждого из 15 условий. Эти timings не используются для FPS A/B.

Итого 57 игровых эпизодов. Между эпизодами 1.8 сек стабилизации, каждый измеряется полные 8 сек, включая позднее окончание частиц и наград. Перед каждым записываются battery temperature/thermal status, WebView version, контекст и геометрия. Изменение ориентации, уход в фон, потеря WebGL и явная отмена прерывают сессию и оставляют неполный отчёт.

Основная метрика: RAF >33.4 мс после округления до 0.1 мс, чтобы Float32 33.4000015 не создавал ложный выигрыш; 33.6 мс телефона сохраняется. Также записываются исходный >33.4, >34, >50, max и p95. Сохраняются все исходные интервалы и end timestamps, окна 0–2.4, 2.4–8 и 0–8 сек. RAF не равен времени физического показа или аппаратного GPU.

Номинация: минимум на 50% меньше длинных интервалов в обоих порядках; max не хуже соседних контролей более чем на 1 мс; drift контролей не больше max(2 интервала, 50% среднего); ≥100 интервалов каждого полного окна; логический/визуальный proof валиден. Номинация не означает готовую оптимизацию. DEV fast и браузерный функциональный запуск никогда не номинируют.

## Содержимое и валидация CDP

Прежний Android TracingController включал privacy filtering и не сохранял DOM/layer/resource identities. Новый preview-only плагин подключается к DevTools **собственного процесса** через abstract LocalSocket. Он не открывает TCP-порт, не подключается к чужим приложениям и ничего не загружает в сеть. Сохраняются unfiltered Trace JSON, LayerTree events, live backend-node descriptions, compositing reasons, Animation events, DOM/layout/style snapshots и именованные app start/committed/end marks.

Это отдельный канал диагностики, не замена renderer. Метаданные и снимки создаются только в traced-части. Обычные сравнительные эпизоды проходят после отключения preflight-соединения и до любого основного CDP-recording.

Проверка не довольствуется `ready=true` от транспорта: нужны Paint с nodeId, реальная связь известного probe с painted layer, native draw и flow, записи узлов, завершённый JSON и известный `dataLossOccurred=false`. Capture ID сопоставляется с ответом stop. Аргументные/событийные лимиты не объявляются успешной записью. Каждая трасса ограничена 128 MiB до gzip, весь session cache — 256 MiB сжатых данных. Файлы пишутся потоково, без загрузки всей трассы в память приложения; отдельно записываются ограничения и ошибки.

На каждый clear проверяются счёт/показанный счёт 1574, pending=0, пустое поле и saved wardrobe=5; фактические темы renderer/DOM palette; число caption/flight/flash/notice/impulse; 148 частиц и два burst, кроме явного no-festival. За полные восемь секунд не должны остаться награды или частицы. Результат, исходные rAF и device samples входят в report; trace/layer/capture файлы связываются именем каталога и capture ID. Экспорт содержит SHA-256/size manifest всех членов.

Если один traced capture невалиден, он не превращается в валидный по наличию файла. Прогон сохраняет оставшиеся результаты. Общий completed требует 57 валидных эпизодов; прерванные/неполные данные не номинируются автоматически. Экспорт ошибки не подхватывает готовую трассу предыдущего запуска.

## Проверки перед выдачей

Подготовлены и выполняются:

- 230 unit; build; 3 целевых browser, включая всю матрицу, независимость переключателей, отказ при пустых identities, отмену и сохранность обычной партии;
- JVM-тесты framing/fragmented UTF-8/ping/close, потокового JSON, пустых identities и обрезанной трассы;
- тот же Java-клиент против реального Chromium: preflight с конкретным узлом и восьмисекундная настоящая очистка;
- CI полной web-регрессии и Android unit/assembly;
- Android emulator: собственный LocalSocket, preflight, весь 57-эпизодный прогон, настоящий экспорт ZIP и независимый Python-анализ архива.

Эмулятор подтверждает Android-транспорт и полноту данных, не производительность Mali. Физический POCO этот вариант ещё не запускал. До завершения проверок APK не считается подготовленным для выдачи.

## Воспроизведение

```sh
npm test
npm run build
npx playwright test e2e/full-clear.spec.ts --workers=1
node scripts/verify-cdp-native.mjs
python scripts/analyze-full-clear.py /path/blocky-full-diagnostic.zip /tmp/full-analysis.json
```

CI для собственного Android capture находится в `cdp-emulator`; реальные share archives и protocol proofs сохраняются как Actions artifacts. Приватный пользовательский ZIP в git не добавляется.
