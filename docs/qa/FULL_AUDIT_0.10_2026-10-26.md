# Полный независимый проход preview 0.10

26.10.2026. Проверен HEAD `23b6cfd3f9447ed2775b1a71c27fa857e57cf5f4`; игровой commit `8048645204d4fe51984ff00e1eaa06b189bdf6e9`. Это свежая проверка исходников, состояния и браузерных сценариев тем же исполнителем, не внешняя экспертиза. Игровой код и APK в этом проходе не менялись.

## Вывод

Основной цикл стал устойчивее: на новой выборке не найдено ошибок очков, очисток, определения конца или потери принятого хода. Последние изменения контакта не сломали транзакционную границу. Есть конкретные пробелы в отображении незавершённых записей и восстановлении после повреждения данных. Для очень короткого портретного окна поле слишком мало, хотя формально ничего не перекрывается.

Проект остаётся игровым preview. Следующий полезный шаг — закрыть эти ограниченные дефекты и провести проверку на телефоне; затем закончить платформенные требования. Оснований для очередного общего редизайна или расширения механик этот проход не дал.

## Свежие доказательства

- Новый oracle: **200 партий, seed 1001…1200, 3 072 принятых хода**, initial-v1, лимит 150 ходов. Допустимые размещения, полные строки/столбцы, объединение удалённых клеток, очки и серия вычислялись отдельно от production `fits/place/clearLines`. Все партии завершились до лимита; расхождений — 0. Сам каталог фигур и выдача остаются production: это независимая проверка хода/конца, не независимая реконструкция всей игры.
- На 34 состояниях из первых десяти партий штатная подсказка всегда допустима; 12 расчётов достигли отсечки. Наблюдаемые времена функции: медиана 1.9 мс, p95 ≈180.1 мс, максимум ≈180.1 мс. Вызов прямой в Chromium: **не включает worker startup, запись, показ и Android**, не закрывает целевой пользовательский p95 ≤300 мс. Оптимальность всех советов этим тестом не доказывается.

В проверенных обычных экранах поле, лоток и подсказка не пересекают нижнюю зарезервированную область; минимальный зазор 5 px. Дополнительно проверен счёт 1 000 000 на 320×568: переполнения не обнаружено. Ненулевые safe-area, обучение и мультитач проверены повторно существующими e2e.
- **100 реальных установок через UI, 3 перезапуска завершённых партий**. Максимум зарегистрированных эффектов — 2, голосов — 6. Через 1.3 с после последнего хода: 0 эффектов, 0 аудиоголосов, 0 DOM-анимаций. Это ограниченная проверка очистки ресурсов; не 30-минутный тест утечек памяти.
- Искусственно задержанные/ошибочные записи, конфликт двух страниц, повреждение одной и обеих копий сохранения. В основном новом probe зарегистрированных pageerror — 0; сообщение об отказе загрузки проверялось отдельно как ожидаемый результат.

## Воспроизведённые проблемы

Это находки текущего прохода, не утверждение, что все они появились именно в 0.10.

### P1 для восстановления: повреждение обеих копий оставляет игрока в тупике

Если `current` повреждён, а `backup` валиден, резервная копия загружается — этот сценарий прошёл. Если обе записи повреждены, `IndexedSave.load()` возвращает `Damaged save`, но общий обработчик старта предлагает закрыть другие вкладки и нажать «Повторить». Повторный запуск читает те же повреждённые записи. Внутри игры нет другого пути восстановления.

Это не воспроизведение самопроизвольного повреждения Android-хранилища: повреждение внесено тестом. Доказана неправильная обработка такого состояния. Данные не затираются — это следует сохранить.

Исправление: различать повреждение, конфликт/блокировку и временную ошибку доступа. Для повреждения — понятное описание, сохранение исходных данных для диагностики и явное действие начала заново с подтверждением потери невосстановимых данных. Для временного отказа повтор должен оставаться безопасным. Не очищать хранилище автоматически.

Источник: `src/platform/save.ts: IndexedSave.load`, `src/main.ts: start().catch`. [Экран](audit-0.10/both-copies-corrupt.png).

### P2: интерфейс паузы не учитывает ожидающий ход

Воспроизведение: задержать `IndexedSave.write` → поставить фигуру → открыть паузу до завершения записи. Показано «Партия сохранена», хотя последний ход ещё не записан и может завершиться ошибкой. Затем «Новая партия» → подтверждение: `ProfileStore.update` возвращает false из-за busy, но `restart()` не сообщает об этом и не блокирует кнопку. Нажатие выглядит неработающим.

Потери или двойного принятия хода не произошло. При отказе записи состояние откатывается корректно, сообщение об ошибке появляется. Проблема — преждевременное обещание сохранения и молчаливый отказ второму действию.

Исправление: общий видимый статус записи и согласованные состояния кнопок паузы/рестарта. До подтверждения записи не писать «сохранена»; повторное действие должно быть явно недоступно с объяснением либо обработано после завершения по определённому правилу.

Источник: `src/main.ts: showPause/restart`, `src/platform/save.ts: ProfileStore.update`. [Экран паузы](audit-0.10/pause-pending.png).

### P2: подсказка теряет индикатор до завершения сохранения

В `worker.onmessage` занятость снимается и подпись обновляется **перед** `await store.update`. При задержанной записи кнопка уже снова выглядит обычной: `aria-busy=null`, текст «Подсказка» скрыт до 1 px, прежний остаток 2. Контур ещё не опубликован; повторное нажатие блокируется внутренним busy без видимого объяснения.

Двойного списания не найдено. Это тот же разрыв обратной связи, который 0.10 закрыл для обычного хода, но ещё не закрыл для подсказки.

Исправление: единый визуальный цикл «расчёт → сохранение → показ», с освобождением busy только после успешного сохранения, отказа или безопасной отмены. Сохранённый receipt должен продолжать восстанавливаться бесплатно.

Источник: `src/main.ts: hint worker.onmessage`. [Экран](audit-0.10/hint-saving.png), точные значения в runtime.json.

### P2 для короткого портрета: поле 152×152 px при 320×480

Клетка — 19 CSS px; лоток — 90 px по высоте, дополнительно остаются значительные вертикальные промежутки. Перекрытия нет, но точное размещение на поле существенно сложнее. На 320×568 поле уже 240×240; на 360×640 — 312×312.

Это геометрическое наблюдение и оценка эргономики, не результат теста пальцем на устройстве. Фиксированное вычитание 328 px из доступной высоты плохо распределяет место в коротком портрете.

Исправление: уточнить минимальную поддерживаемую высоту, перераспределить вертикальный бюджет в коротком режиме, сохраняя зоны основных кнопок. Проверять не только отсутствие пересечений, но и фактический размер клеток. [320×480](audit-0.10/screen-320x480.png), [320×568](audit-0.10/screen-320x568.png).

### P3, преимущественно web: конфликт сохранения требует другого сообщения

Две страницы загрузили одну ревизию. Первая записала ход, вторая попыталась записать отличный ход на той же ревизии: сохранение правильно отвергло конфликт. Но второй странице предлагают просто повторить ход; её локальное состояние остаётся старым, поэтому нужен reload/перечитывание. После reload принятой первой страницей ход на месте, счёт 1.

Для текущего Android `singleTask` это менее типичный сценарий. До публичной web-версии различить конфликт и обычный отказ записи; не подавать повтор по старой ревизии как способ восстановления.

## UI, UX и feel

**Сильные стороны.** Поле читается, лоток не меняет порядок, preview показывает будущую очистку, текущая доступность фигур различима. Установка и награды имеют общий звуковой контакт; визуальная очистка связана с поставленной фигурой. Косметика допускает следующие ходы и очищается при паузе. Спокойный режим сохранён. Миллионный счёт в проверенном компактном портрете помещается.

**Что пока не доказано.** Приятность новой атаки звука, различимость четырёх артикуляций на дешёвом динамике, утомление через 20 минут, точность переноса большим пальцем и удовольствие от серии. Сам факт синтеза/лимитов не даёт этих ответов. Нового прослушивания на физическом телефоне не было.

**Моя визуальная оценка.** Композиция соответствует понятному казуальному блок-пазлу. Собственный характер выражен слабо: фон, корона, лампочка, гранёные квадраты и оформление паузы остаются довольно общими. Дополнительная палитра или частицы сами по себе не решат эту задачу. Если продолжать художественную работу, ограничить её одним цельным проходом по наградам, результату и звуковому характеру после просмотра владельцем на телефоне.

**Мотивация и баланс.** Правила понятны из помощи, но ясность проигрыша и желание повторять не подтверждены людьми. 4 000 симуляций 0.9 — существующее доказательство поведения двух ботов; они не проводились заново и не являются удержанием. В новом проходе 200 партий использованы для корректности, не для выбора выдачи. Политика initial-v1 остаётся прежней; оснований переключить её автоматически нет.

## Производительность и поддерживаемость

За одинаковые окна наблюдения 1.2 с: без действий 72 postrender и 0 повторных вызовов `BoardScene.draw`; с подсказкой 72 postrender и 72 draw; на паузе 0/0. Суммарное измеренное время draw при подсказке — около 6.6 мс на этом Chromium. Это CPU-время обёртки JS, **не** GPU-профиль, батарея или fps телефона. Фоновая/паузная остановка работает; на активном статичном экране рендер продолжает идти около 60 раз/с.

Кандидат на последующую оптимизацию — рендер по необходимости для статичного поля, с возобновлением при жесте/подсказке/эффекте. Сейчас это не подтверждённый performance blocker. Измерять на целевом Android прежде, чем усложнять цикл Phaser. Подсказка уже ограничена бюджетом и вынесена в worker; допускать её блокировку основного потока нельзя.

Production bundle: Phaser 1 367.08 kB (gzip 357.00 kB), основной JS 46.77 kB, worker 4.31 kB, CSS 13.47 kB. Для APK файлы локальные: размер чанка сам по себе не доказывает медленный запуск. Замена движка или дополнительное дробление без профиля не обоснованы.

Правила, профиль, storage, audio и сцена разделены. `main.ts` объединяет навигацию, управление, обучение и несколько асинхронных процессов. Найденные busy-дефекты показывают конкретную точку улучшения: единообразно управлять фазами записи. Выделять новый универсальный движок или масштабно переписывать весь UI для этого не требуется. Каскад CSS содержит последовательные переопределения прошлых версий; при правке короткого портрета стоит собрать соответствующие правила в одно место и сохранить матрицу размеров.

## Следующий пакет

1. **Состояния сохранения:** пауза, рестарт, подсказка; регрессии success/failure/background во время каждой операции.
2. **Восстановление:** различение причин отказа загрузки, безопасный выход из повреждения обеих копий, понятное разрешение конфликта. Никакого автоматического удаления данных.
3. **Короткий портрет:** перераспределение места под поле, проверка 320×480 и всей существующей матрицы с insets/обучением/длинными сообщениями.
4. **Телефонный checkpoint:** установка поверх 0.10, точность жеста, быстрые очистки, звук на низкой громкости, 20–30 минут, фон/поворот/Back. Результаты использовать для решения о дальнейшем feel.
5. **Затем завершение M1/M4:** тестовый native ad SDK и audio focus, далее устойчивые reward-транзакции/монетизация/аналитика по ТЗ. Не считать магазинный релиз готовым после косметических исправлений.

Новые режимы, метапрогресс и ещё один общий редизайн не предлагаются. Открытые продуктовые и аппаратные gates остаются открытыми.
